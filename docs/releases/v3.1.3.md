# Nowlert CE v3.1.3 release notes

Nowlert CE v3.1.3 is a documentation and discoverability patch release on the
v3.1.x line. It does not change event-ingestion, parser, routing, destination,
authentication, database-schema, or backup behavior.

It keeps database schema **9** and the **`platform_database_v1`** configuration
model. No database migration is required from v3.1.2.

## Highlights

### Practical operator guides

v3.1.3 adds a consolidated set of current end-to-end use-case guides:

- Xen Orchestra → SMTP → Nowlert CE → Discord;
- Xen Orchestra → SMTP → Nowlert CE → Microsoft Teams;
- direct homelab SMTP ingestion without mailbox forwarding/rules;
- Dell iDRAC → Redfish → Nowlert CE routing; and
- Zabbix → authenticated Event API → Nowlert CE → Discord.

The guides use the current WebUI/database-authoritative destination, route, and
token model rather than legacy YAML-managed resource examples.

### Documentation navigation cleanup

- Adds a stable `docs/integrations/` index for the integration path already
  referenced by the README/current documentation.
- Preserves the existing top-level integration-guide paths so historical and
  inbound links are not broken by an unnecessary file move.
- Adds a dedicated `docs/guides/` index for practical end-to-end flows.

### Release batching

The documentation work for the active CE marketing tasks is intentionally
batched into one CE patch candidate. This avoids repeated Development → Stage →
Production Reference → release cycles for individual documentation additions.

## Compatibility

- Database schema: **9**
- Configuration model: **`platform_database_v1`**
- Persistent state path: **`/nowlert/state`**
- Python: **3.13**
- Existing v3.1.2 state can be used directly.
- Existing `NOWLERT_*` environment variables and `/api/v2` management contract
  remain unchanged.
- No runtime behavior or database migration is introduced by this release.

## Upgrade from v3.1.2

1. Record the currently running image/version.
2. Retain the normal matched backup of `config`, `state`, and external
   `secrets` before deployment.
3. Pull/pin `theriark/nowlert-ce:3.1.3` or the published immutable digest.
4. Redeploy with the existing `/nowlert` mounts unchanged.
5. Verify `/api/health` reports `3.1.3`.
6. Verify normal login, routes, destinations, Delivery History, Audit Log,
   Users, and Backups.

## Release provenance

The v3.1.3 candidate is version-complete on `development` before the Development
image is built. One immutable GHCR digest is then promoted through Stage and
Production Reference without rebuild.

After Production Reference approval, the release finalizer must prove that:

- current `main` equals the approved source commit;
- source `VERSION` is exactly `3.1.3`;
- the requested release version is exactly `v3.1.3`;
- these release notes and the v3.1.3 QA checklist exist on that source commit;
- Development, Stage, and Production Reference evidence all refer to the same
  source SHA and immutable image digest.

Only then is the annotated `v3.1.3` tag and GitHub Release created. Stable GHCR
and Docker Hub `3.1.3`/`latest` aliases are copies of that same approved digest;
they are not rebuilt from the tag.

## Rollback

Because v3.1.3 introduces no schema migration or runtime contract change,
rollback to the previously approved v3.1.2 image is straightforward. Preserve
the normal matched backup, pin the previous immutable image/digest, and verify
health and routing before restoring normal traffic.

See the [v3.1.3 QA checklist](../v3.1.3-qa-checklist.md) and
[deployment/release guide](../deployment.md).
