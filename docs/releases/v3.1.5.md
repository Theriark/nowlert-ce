# Nowlert CE v3.1.5 release notes

Nowlert CE v3.1.5 is a release-maintenance patch that consolidates the
Community Edition repository around the current Stage-final release model. It
preserves v3.1.x runtime behavior while updating release identity, repository
automation, and current release-policy documentation.

It keeps database schema **9** and the **`platform_database_v1`** configuration
model. No database migration is required from v3.1.4.

## Highlights

### Release automation cleanup

The active CE release path remains:

```text
Development -> Stage -> main -> Release
```

- Development builds the candidate once and records the immutable GHCR digest.
- Stage runs the full notification-silent acceptance gate, deploys that exact
  digest, verifies live health and passive smoke, records desired state, and
  advances the `stage` source branch.
- `main` is advanced only by a guarded fast-forward to the exact Stage-approved
  source commit.
- Release finalization verifies `main == stage == source commit`, validates the
  Development and Stage evidence, checks live Stage state and desired-state
  evidence, and then creates the annotated tag and GitHub Release.
- Stable GHCR and Docker Hub version/`latest` aliases are copied from the same
  approved digest without rebuilding the application.

v3.1.5 removes obsolete repository automation left behind by previous release
models. The active GitHub Actions set is limited to Continuous Integration,
Development Image, Docker Release Aliases, Finalize CE Release, and Promote CE
to Stage. Obsolete CE runtime-drift automation and Dependabot configuration are
removed, and the maintained branch set is `development`, `stage`, and `main`.

### Release-policy documentation cleanup

Current contribution and roadmap documentation now describes Stage as the final
live runtime gate and `main` as the exact Stage-approved release source.
Historical release notes and acceptance checklists remain unchanged as records
of the process that existed when those versions shipped.

## Compatibility

- Database schema: **9**
- Configuration model: **`platform_database_v1`**
- Persistent state path: **`/nowlert/state`**
- Python: **3.13**
- Existing v3.1.4 state can be used directly.
- Existing `NOWLERT_*` environment variables and `/api/v2` management contract
  remain unchanged.
- Event ingestion, parsers, routing, destinations, authentication, backups, and
  WebUI behavior are unchanged by this maintenance release.

## Upgrade from v3.1.4

1. Record the currently running image/version and immutable digest.
2. Retain the normal matched backup of `config`, `state`, and external
   `secrets` before deployment.
3. Pull/pin `theriark/nowlert-ce:3.1.5` or the published immutable digest.
4. Redeploy with the existing `/nowlert` mounts unchanged.
5. Verify `/api/health` reports `3.1.5`.
6. Verify normal login, routes, destinations, Delivery History, Audit Log,
   Users, and Backups.

## Release provenance

The v3.1.5 candidate is version-complete on `development` before the Development
image is built. That build produces one immutable GHCR digest. Stage promotes
that exact digest without rebuild and remains the final runtime acceptance gate.

After Stage approval, `main` is fast-forwarded to the same approved source
commit. The release finalizer must then prove that:

- current `main` equals current `stage` and the requested source commit;
- source `VERSION` is exactly `3.1.5`;
- the requested release version is exactly `v3.1.5`;
- these release notes and the v3.1.5 QA checklist exist on that source commit;
- Development and Stage evidence refer to the same source SHA and immutable
  image digest;
- live Stage reports the expected version and exact image; and
- Stage desired-state evidence matches the approved candidate.

Only then is the annotated `v3.1.5` tag and GitHub Release created. Stable GHCR
and Docker Hub `3.1.5`/`latest` aliases are registry copies of that approved
digest; they are not rebuilt from the tag.

## Rollback

v3.1.5 introduces no schema migration or runtime contract change. Preserve the
normal matched backup, pin the previously approved v3.1.4 image/digest, and
verify health and routing before restoring normal traffic.

See the [v3.1.5 QA checklist](validation/v3.1.5-qa-checklist.md) and
[deployment/release guide](../deployment.md).
