# Nowlert CE v3.1.4 release notes

Nowlert CE v3.1.4 is a release-engineering maintenance patch that makes Stage
the final runtime acceptance gate for Community Edition releases. It preserves
the v3.1.x runtime behavior while updating the release identity, documentation,
and automated release evidence for the simplified promotion chain.

It keeps database schema **9** and the **`platform_database_v1`** configuration
model. No database migration is required from v3.1.3.

## Highlights

### Stage-final release chain

The active CE release path is now:

```text
Development -> Stage -> main -> Release
```

- Development builds the candidate once and records the immutable GHCR digest.
- Stage runs the full notification-silent test gate, deploys that exact digest,
  verifies live health and passive smoke, records desired state, and advances
  the `stage` source branch.
- `main` is advanced only by a guarded fast-forward to the exact Stage-approved
  source commit.
- Release finalization verifies `main == stage == source commit`, validates the
  Development and Stage evidence, checks the live Stage digest and ledger, and
  then creates the annotated tag and GitHub Release.
- Stable GHCR and Docker Hub version/`latest` aliases are copied from the same
  approved digest without rebuilding the application.

### Release provenance cleanup

v3.1.4 makes the release evidence match the actual CE acceptance boundary:
Stage is the final live runtime gate, while `main` and the release tag identify
the exact approved source. The release workflow does not perform another CE
application deployment.

## Compatibility

- Database schema: **9**
- Configuration model: **`platform_database_v1`**
- Persistent state path: **`/nowlert/state`**
- Python: **3.13**
- Existing v3.1.3 state can be used directly.
- Existing `NOWLERT_*` environment variables and `/api/v2` management contract
  remain unchanged.
- Event ingestion, parsers, routing, destinations, authentication, backups, and
  WebUI behavior are unchanged by this maintenance release.

## Upgrade from v3.1.3

1. Record the currently running image/version and immutable digest.
2. Retain the normal matched backup of `config`, `state`, and external
   `secrets` before deployment.
3. Pull/pin `theriark/nowlert-ce:3.1.4` or the published immutable digest.
4. Redeploy with the existing `/nowlert` mounts unchanged.
5. Verify `/api/health` reports `3.1.4`.
6. Verify normal login, routes, destinations, Delivery History, Audit Log,
   Users, and Backups.

## Release provenance

The v3.1.4 candidate is version-complete on `development` before the Development
image is built. That build produces one immutable GHCR digest. Stage promotes
that exact digest without rebuild and becomes the final runtime acceptance gate.

After Stage approval, `main` is fast-forwarded to the same approved source
commit. The release finalizer must then prove that:

- current `main` equals current `stage` and the requested source commit;
- source `VERSION` is exactly `3.1.4`;
- the requested release version is exactly `v3.1.4`;
- these release notes and the v3.1.4 QA checklist exist on that source commit;
- Development and Stage evidence refer to the same source SHA and immutable
  image digest;
- live Stage reports the expected version and exact image; and
- the Stage desired-state ledger matches the approved candidate.

Only then is the annotated `v3.1.4` tag and GitHub Release created. Stable GHCR
and Docker Hub `3.1.4`/`latest` aliases are registry copies of that approved
digest; they are not rebuilt from the tag.

## Rollback

v3.1.4 introduces no schema migration or runtime contract change. Preserve the
normal matched backup, pin the previously approved v3.1.3 image/digest, and
verify health and routing before restoring normal traffic.

See the [v3.1.4 QA checklist](validation/v3.1.4-qa-checklist.md) and
[deployment/release guide](../deployment.md).
